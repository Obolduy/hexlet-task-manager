# 002 — Фильтрация задач по исполнителю и статусу

Источник: issue #11 «Фильтрация задач в списке». Список задач вырос,
нужно уметь отобрать задачи по исполнителю и по статусу, оба фильтра
должны применяться одновременно (комбинация через И).

## Объём

Входит: фильтр по конкретному исполнителю (`assignee_id`), фильтр по
статусу, совместное применение обоих.

Не входит:
- фильтр «без исполнителя» (`assignee_id is null`) — issue просит фильтр
  «по исполнителю», это выбор конкретного пользователя, а не отдельного
  псевдо-значения; не запрошено, добавлять не нужно;
- пагинация, сортировка, сохранение фильтров в URL, debounce — в issue не
  упомянуты.

## Бэкенд (`apps/api`)

### Слои

- `routes/tasks.py` — `GET /tasks` получает два новых необязательных
  query-параметра, передаёт их дальше без интерпретации.
- `services/task_service.py` — `list_tasks` принимает те же
  необязательные фильтры и пробрасывает их в модельный слой. Валидировать
  тут нечего: значение статуса уже проверено Pydantic/enum на уровне
  роута, а несуществующий `assignee_id` для фильтра — не ошибка (см.
  контракт ниже), в отличие от `create_task`, где `AssigneeNotFound`
  проверяет существование при записи.
- `models/task.py` — `list_tasks` строит `WHERE` динамически: список
  условий и параметров собирается по наличию фильтров, соединяется через
  `and`, значения передаются только через `?`-плейсхолдеры (не
  форматированием строки — иначе SQL-инъекция).

### Контракт

`GET /tasks?status=<status>&assignee_id=<id>`

- `status` — необязательный, одно из значений `TaskStatus`
  (`new` / `in_progress` / `in_review` / `done`), тот же enum, что уже
  используется в `TaskStatusUpdate`. Невалидное значение → `422`
  (автоматически, как и сейчас для тела `PATCH /tasks/{id}/status`).
- `assignee_id` — необязательный `int`. Существование пользователя не
  проверяется: несуществующий `assignee_id` — это просто фильтр без
  совпадений, ответ `200` с пустым списком, а не `422`. Это осознанно
  отличается от `TaskCreate.assignee_id`, где несуществующий пользователь
  — ошибка, потому что там это команда на запись, а не фильтр на чтение.
- Оба параметра независимы; если переданы оба — условия объединяются через
  И.
- Без параметров поведение не меняется (весь список, `order by id`).
- Форма ответа не меняется — `list[TaskOut]`, те же поля.

### Тесты (`apps/api/tests/test_tasks.py`, добавить к существующим)

- `test_list_tasks_filtered_by_status_returns_only_matching` — `?status=done`
  возвращает только задачи со статусом `done`.
- `test_list_tasks_filtered_by_assignee_returns_only_matching` — `?assignee_id=<id>`
  возвращает только задачи этого исполнителя.
- `test_list_tasks_filtered_by_status_and_assignee_combined` — оба параметра
  вместе, в ответе — только задачи, удовлетворяющие обоим условиям сразу.
- `test_list_tasks_filtered_by_invalid_status_is_rejected` — `?status=archived`
  → `422`.
- `test_list_tasks_filtered_by_unknown_assignee_returns_empty_list` —
  `?assignee_id=9999` → `200`, пустой список (фиксирует отличие от
  `AssigneeNotFound` в `create_task`, см. контракт).

Ожидаемые количества по фильтрам не хардкодить как магические числа —
сравнивать с подмножеством уже пройденного через `GET /tasks` без
фильтров (сиды детерминированы, `SEED_RANDOM_SEED=42`, но независимость
теста от деталей распределения важнее).

## Фронтенд (`apps/web`)

### Слои

- `api/types.ts` — новый тип `TaskFilters` (`{ status: TaskStatus | null;
  assigneeId: number | null }`), используется в `api/tasks.ts`,
  `TaskScreen.vue` и `TaskFilters.vue`.
- `api/tasks.ts` — `fetchTasks` принимает необязательный `TaskFilters`,
  собирает query-строку (`assigneeId` → `assignee_id`, аналогично уже
  существующему мэппингу snake_case/camelCase в `mapTask`). Формат ответа
  и `mapTask` не меняются.
- `components/TaskFilters.vue` (новый) — презентационный компонент без
  side-effects: два `<select>` (статус, исполнитель). Получает список
  пользователей и текущие значения фильтров через props, о выборе
  сообщает событиями (`update:status`, `update:assigneeId`) — данные
  наружу компонент не запрашивает, это входит в правило «к `api/`
  обращается только `TaskScreen.vue`».
- `components/TaskScreen.vue` — держит состояние обоих фильтров, грузит
  пользователей один раз при монтировании, грузит задачи через
  `fetchTasks(filters)` при монтировании и при каждом изменении фильтров;
  рендерит `TaskFilters` над `TaskList`.
- `components/TaskList.vue`, `TaskListItem.vue` — не меняются, получают
  уже отфильтрованный список задач через props, как и сейчас.

### Контракт компонента

`TaskFilters.vue`:
- props: `users: User[]`, `status: TaskStatus | null`, `assigneeId: number
  | null`;
- events: `update:status` (`TaskStatus | null`), `update:assigneeId`
  (`number | null`).

### Тесты (`apps/web/tests`)

- `TaskFilters.spec.ts` (новый, компонент с логикой — по правилу минимум
  один тест): опции статуса и список пользователей рендерятся из props;
  выбор статуса эмитит `update:status`; выбор исполнителя эмитит
  `update:assigneeId`.
- `TaskList.spec.ts` — без изменений, `TaskList.vue` не трогается.

## Отступления и границы

- `TaskScreen.vue` сейчас вообще не покрыт тестами (в `apps/web/tests` нет
  файла ни для одного компонента с side-effects). Новая логика фильтрации
  (доп. `ref`ы, `watch`, повторный вызов `fetchTasks`) добавляется в него
  по уже существующему прецеденту непокрытого side-effects-компонента;
  заводить тест на `TaskScreen.vue` — отдельная задача не в объёме этой
  спеки, не предлагать чинить попутно.
- Отклонений от правил `apps/api/AGENTS.md` и `apps/web/AGENTS.md` в этой
  задаче нет: изменения остаются в существующих слоях (`routes` →
  `services` → `models` для задач; `api/` только из `TaskScreen.vue`).
