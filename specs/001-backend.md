# Спека 001 — бэкенд демо-монорепы (apps/api)

Базовая версия сервиса управления задачами. Реализуется до эфира и должна быть
в зелёном CI на момент старта — задача с эфира (фильтрация) добавляется поверх
этой версии отдельной веткой и в эту спеку не входит.

## 1. Границы

Входит: apps/api — слои routes/services/models, 5 эндпоинтов, схема SQLite,
сид, тесты.

Не входит: apps/web, knowledge-service, review-action, workflows, issue с
задачей на эфир. Команды запуска/тестирования и правила PR — в
`AGENTS.md`, здесь не дублируются.

## 2. Структура apps/api

```
apps/api/
  src/
    main.py              # создание FastAPI-приложения, подключение роутов
    db.py                 # соединение с SQLite, создание схемы, запуск сида
    seed.py                # данные сида (5 пользователей, 50 задач)
    schemas.py            # pydantic-модели запросов/ответов
    models/
      task.py             # SQL-запросы по задачам
      user.py              # SQL-запросы по пользователям
    services/
      task_service.py     # бизнес-логика задач, единственный сервисный модуль
    routes/
      tasks.py             # 4 роута задач
      users.py              # 1 роут пользователей
  tests/
    conftest.py            # фикстуры: временная БД, тестовый клиент, сид
    test_tasks.py
    test_users.py
```

Слои: `routes` вызывает `services`, `services` вызывает `models`. `models` —
единственное место с SQL. Один эндпоинт из этого правила сознательно выпадает
(см. раздел 6).

## 3. Модель данных

```sql
create table users (
  id     integer primary key autoincrement,
  name   text not null,
  email  text not null unique
);

create table tasks (
  id           integer primary key autoincrement,
  title        text not null,
  description  text,
  status       text not null default 'new',
  assignee_id  integer references users(id),
  created_at   text not null,
  updated_at   text not null
);
```

Статусы задачи — плоский набор значений без хранимой семантики переходов:
`new`, `in_progress`, `in_review`, `done`. Любой валидный статус можно
сменить на любой другой; правил вида «нельзя в `done`, минуя `in_review`»
на этом уровне нет — это осознанное решение о границе модели (см. раздел 6.3
про соответствующий пропущенный тест), а не недосмотр.

`assignee_id` допускает `NULL` — задача может быть без исполнителя.

### Сид

- 5 пользователей с разными именами и уникальными email.
- 50 задач, распределённых по всем 4 статусам неравномерно (не поровну —
  чтобы будущая фильтрация по статусу давала разные по размеру выборки).
  Часть задач (5–10) без `assignee_id` — понадобится для будущей фильтрации
  по исполнителю и для проверки поведения с пустым значением.
- Сид выполняется при создании таблиц, если они пустые; повторный старт
  приложения не дублирует данные.

## 4. Эндпоинты

Формат ошибок — стандартный FastAPI: `HTTPException` с телом
`{"detail": "..."}`. Отдельного envelope нет.

### 4.1 `GET /tasks`

Без параметров запроса в этой версии (параметры фильтрации — предмет
будущей задачи, не этой спеки).

Ответ `200`: массив объектов задачи.

```json
{
  "id": 1,
  "title": "string",
  "description": "string | null",
  "status": "new | in_progress | in_review | done",
  "assignee_id": "int | null",
  "created_at": "ISO 8601",
  "updated_at": "ISO 8601"
}
```

### 4.2 `POST /tasks`

Тело запроса:

```json
{ "title": "string (обязательно, не пустая)", "description": "string | null", "assignee_id": "int | null" }
```

- `status` в теле не принимается, всегда выставляется `new`.
- Если `title` пустой или отсутствует — `422` (стандартная pydantic-валидация).
- Если `assignee_id` передан и такого пользователя нет — `422` с
  `detail: "assignee_id does not reference an existing user"`.
- Успех — `201`, тело — созданный объект задачи (формат как в 4.1).

### 4.3 `GET /tasks/{id}`

- Найдена — `200`, объект задачи.
- Не найдена — `404`, `detail: "task not found"`.

### 4.4 `PATCH /tasks/{id}/status`

Тело запроса: `{ "status": "new | in_progress | in_review | done" }`.

- Значение вне набора — `422` (pydantic Enum, проверяется до обращения к
  сервисному слою).
- Задача не найдена — `404`, `detail: "task not found"`.
- Переход разрешён всегда, без проверки «откуда куда» (см. раздел 3).
- Успех — `200`, обновлённый объект задачи, `updated_at` меняется.

### 4.5 `GET /users`

Без параметров.

Ответ `200`: массив объектов пользователя.

```json
{ "id": 1, "name": "string", "email": "string" }
```

## 5. Слои: реализация

- `schemas.py` — `TaskCreate`, `TaskStatusUpdate` (с `Enum` статуса),
  `TaskOut`, `UserOut`.
- `models/task.py` — функции `list_tasks`, `create_task`, `get_task`,
  `update_task_status`, каждая принимает соединение и примитивные аргументы,
  возвращает dict/row, SQL — только здесь.
- `services/task_service.py` — то же название операций на уровне бизнес-логики:
  `list_tasks`, `create_task` (проверка `assignee_id`), `get_task`,
  **`set_status`** (см. раздел 6.2 — сознательное отступление от нейминга).
- `routes/tasks.py` — 4 роута из 4.1–4.4, каждый вызывает соответствующий
  метод `task_service`, конвертирует в `TaskOut`.
- `models/user.py` — функция `list_users`.
- `routes/users.py` — роут 4.5 вызывает `models/user.py` напрямую (см.
  раздел 6.1).

## 6. Осознанные отступления

Ниже — не баги и не техдолг, а намеренные элементы кодовой базы для демонстрации
на эфире: агент должен на них наткнуться в акте 1–2, а ревьюер в CI — найти во
втором акте. Не предлагать исправление, не помечать TODO/FIXME.

### 6.1 Обход сервисного слоя в `GET /users`

`routes/users.py` вызывает `models/user.py` напрямую, без
`services/user_service.py` — такого модуля в кодовой базе нет вообще.
Это старейший эндпоинт проекта, написанный до того, как оформилось правило
«роуты не ходят в модели напрямую». Остальные 4 эндпоинта через сервисный
слой проходят.

### 6.2 Неконсистентный нейминг в `services/task_service.py`

Три метода следуют паттерну `<действие>_task[s]`: `list_tasks`,
`create_task`, `get_task`. Четвёртый — `set_status` — выбивается из
паттерна и по названию не сразу понятно, чей статус он меняет
(должно было быть `update_task_status`). Роут `routes/tasks.py` вызывает
именно `set_status`.

### 6.3 Пропущенный тест

В `tests/test_tasks.py` один тест помечен
`@pytest.mark.skip(reason="починить после рефакторинга")`. Тест проверяет,
что прямой переход `new → done` минуя `in_review` отклоняется — то есть
фиксирует ожидаемое поведение, которого сейчас нет (см. раздел 3: переходы
не валидируются). Тест не удалять и не чинить в рамках этой спеки.

## 7. Тесты

10–15 тестов, pytest + `TestClient` из FastAPI. Изолированная SQLite-БД на
тестовый прогон (временный файл или `:memory:`), сид применяется в фикстуре.

`test_tasks.py`:
- `GET /tasks` возвращает список ожидаемой длины после сида.
- `POST /tasks` с валидным телом — `201`, поля в ответе совпадают с телом
  запроса, `status == "new"`.
- `POST /tasks` без `title` — `422`.
- `POST /tasks` с несуществующим `assignee_id` — `422`.
- `GET /tasks/{id}` для существующей задачи — `200`.
- `GET /tasks/{id}` для несуществующего id — `404`.
- `PATCH /tasks/{id}/status` с валидным статусом — `200`, `updated_at`
  изменился.
- `PATCH /tasks/{id}/status` с невалидным значением — `422`.
- `PATCH /tasks/{id}/status` для несуществующей задачи — `404`.
- Пропущенный тест на запрет `new → done` (раздел 6.3).

`test_users.py`:
- `GET /users` возвращает список ожидаемой длины после сида, поля
  соответствуют схеме.
