# 003 — Быстрое завершение задачи из списка

Issue: #15.

Сейчас перевод задачи в статус «Готово» требует перехода на отдельный экран.
Нужно действие прямо в списке, в один клик.

## Принятые решения

Задача умышленно не расписывает детали реализации — фиксирую то, что решено
по ходу.

- **Эндпоинт**: переиспользуется существующий `PATCH /tasks/{id}/status`
  (`apps/api/src/routes/tasks.py`). Отдельный эндпоинт не создаётся — он
  дублировал бы уже существующую логику `task_service.set_status` без
  дополнительной пользы. Бэкенд не меняется: ни `routes/`, ни `services/`,
  ни `models/`.
- **Ограничения «кто и когда может завершить»**: в проекте нет аутентификации
  и пользовательских сессий (`apps/api/src/main.py`, `routes/users.py` — не
  выдают токен, не проверяют личность). Ограничивать действие некем и нечем,
  поэтому ограничений на завершение задачи нет — вне объёма задачи.
- **Существующий `pytest.mark.skip`** в `apps/api/tests/test_tasks.py`
  (`test_direct_transition_from_new_to_done_is_rejected`) описывает
  потенциальное будущее правило «нельзя перейти из `new` сразу в `done`».
  Сейчас оно не реализовано: `set_status` принимает любой переход. Кнопка
  «Завершить» вызывает тот же самый `PATCH /tasks/{id}/status`, что и любая
  другая смена статуса — специальной логики в обход сервиса не добавляется.
  Если правило перехода появится позже, кнопка автоматически станет ему
  подчиняться без доработки. Тест по правилам `apps/api/AGENTS.md` не
  трогать.
- **Синхронизация состояния**: после успешного ответа локальная задача в
  списке обновляется данными из ответа `PATCH` (сервер — источник истины
  для `status`/`updated_at`), без повторного `GET /tasks`.
- **Видимость кнопки**: показывается только для задач со статусом не
  `done` — действие «завершить уже готовую задачу» бессмысленно.

## Структура и слои затронутого кода

Изменения только во фронтенде, слой `api/` не расширяется новым модулем —
дополняется существующий.

- `apps/web/src/api/tasks.ts` — новая функция `completeTask(id)`, вызывающая
  `PATCH /tasks/{id}/status` с `{ status: 'done' }` и возвращающая
  замапленный `Task`.
- `apps/web/src/components/TaskScreen.vue` — единственный компонент,
  обращающийся к `api/` (правило `apps/web/AGENTS.md`). Добавляет:
  - `completingTaskId: Ref<number | null>` — id задачи в процессе
    завершения, для блокировки повторного клика;
  - `completeError: Ref<string | null>` — текст ошибки последней попытки
    завершения (отдельно от `error` начальной загрузки, чтобы не подменять
    весь список сообщением об ошибке);
  - обработчик `handleComplete(taskId)`, вызывающий `completeTask`,
    обновляющий соответствующий элемент `tasks.value` по id при успехе.
- `apps/web/src/components/TaskList.vue` — прокидывает `completingTaskId`
  вниз и ретранслирует событие `complete` вверх. Без собственной логики.
- `apps/web/src/components/TaskListItem.vue` — кнопка «Завершить» и её
  состояния (скрыта/disabled). Без side-effects, как и раньше.

## Контракты

### Backend: `PATCH /tasks/{id}/status` (без изменений, используется как есть)

- Request body: `{"status": "done"}` (схема `TaskStatusUpdate`).
- Response `200`: `TaskOut` — полная задача с обновлёнными `status` и
  `updated_at`.
- Response `404`: задача не найдена.
- Response `422`: невалидное значение `status` (не наш случай — значение
  всегда `"done"`, задаётся кодом, не пользователем).

### Frontend

`api/tasks.ts`:

```ts
function completeTask(id: number): Promise<Task>
```

Бросает `Error` при не-`ok` ответе — по тому же принципу, что и
`fetchTasks`.

`TaskListItem.vue`:

- props: `task: Task`, `assigneeName: string | null` (без изменений),
  `+ isCompleting: boolean`;
- emits: `complete: [taskId: number]`;
- кнопка рендерится через `v-if="task.status !== 'done'"`, блокируется
  через `:disabled="isCompleting"`.

`TaskList.vue`:

- props: `tasks`, `assigneeNameById` (без изменений),
  `+ completingTaskId: number | null`;
- emits: `complete: [taskId: number]` — ретрансляция события от
  `TaskListItem`.

`TaskScreen.vue` — обработчик по контракту:

- при клике — `completingTaskId = taskId`, `completeError = null`;
- при успехе — замена задачи в `tasks.value` данными из ответа,
  `completingTaskId = null`;
- при ошибке — `completeError` выставляется в текст сообщения,
  `completingTaskId = null`, задача в списке не меняется (кнопка остаётся
  доступной для повтора).

## Состав тестов

Backend (`apps/api/tests/test_tasks.py`, без изменений в проверяемом коде,
эндпоинт уже покрыт — добавляется один тест на конкретно тот вызов, на
который опирается новая фича):

- `PATCH /tasks/{id}/status` с `{"status": "done"}` на задаче со статусом
  `new` (сид по умолчанию) переводит её в `done` и меняет `updated_at` —
  фиксирует контракт, на который опирается кнопка «Завершить», отдельно от
  уже существующего теста с переходом в `in_progress`.

Frontend:

- `apps/web/tests/TaskListItem.spec.ts` (новый файл):
  - кнопка «Завершить» рендерится при `task.status !== 'done'`;
  - кнопка отсутствует при `task.status === 'done'`;
  - клик по кнопке эмитит `complete` с `task.id`;
  - при `isCompleting: true` кнопка `disabled`.
- `apps/web/tests/TaskList.spec.ts` (дополняется):
  - клик по кнопке завершения на элементе списка ретранслируется наружу
    как событие `complete` с правильным id;
  - `completingTaskId` доходит до нужного `TaskListItem` как `isCompleting`.
- `apps/web/tests/TaskScreen.spec.ts` (новый файл, `api/tasks` и
  `api/users` мокаются через `vi.mock`):
  - успешное завершение обновляет статус нужной задачи в отрисованном
    списке;
  - ошибка запроса не меняет статус задачи и показывает сообщение об
    ошибке;
  - на время запроса кнопка соответствующей задачи заблокирована.

## Отступления от общих правил

Новых отступлений задача не вводит. Затрагивает код, использующий уже
задокументированное в `apps/api/AGENTS.md` исключение — метод
`task_service.set_status` (а не `update_task_status`) — но не меняет его,
переименовывать не требуется.
