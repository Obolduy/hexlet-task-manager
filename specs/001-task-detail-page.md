# 001 — Страница деталей задачи

Источник: issue [#19](https://github.com/Obolduy/hexlet-task-manager/issues/19)
«Открывать детали задачи на отдельной странице». Сейчас информация о
задаче видна только в карточке в общем списке. Нужно, чтобы по клику на
задачу открывался отдельный экран с её полной информацией, доступный по
прямой ссылке — чтобы можно было поделиться URL на конкретную задачу.

## Объём

Входит:
- отдельный URL вида `/tasks/{id}` на конкретную задачу;
- переход туда по клику из списка, без перезагрузки страницы;
- открытие этого URL напрямую (по прямой ссылке, включая обновление
  страницы) показывает тот же экран деталей;
- отображение полной информации о задаче: название, статус, описание,
  исполнитель, даты создания/обновления;
- состояния загрузки, ошибки и «задача не найдена»;
- переход назад к списку.

Не входит:
- редактирование или удаление задачи с экрана деталей — issue просит
  только просмотр;
- `vue-router` или любая другая библиотека роутинга — запрещено
  `apps/web/AGENTS.md` («Без роутера»), и для двух статичных экранов
  отдельная зависимость не оправдана;
- отдельная страница 404 для неизвестных путей — см. «Открытые вопросы»;
- хлебные крошки, анимации переходов, история «предыдущая/следующая
  задача», пагинация, фильтры.

## Фронтенд (`apps/web`)

Новых зависимостей не добавляется. Вместо `vue-router` — свой минимальный
модуль навигации поверх `history.pushState` + `popstate`. `nginx.conf`
уже настроен на `try_files $uri $uri/ /index.html`
([nginx.conf:13-15](../apps/web/nginx.conf#L13-L15)), поэтому открытие
`/tasks/7` напрямую будет работать без изменений в инфраструктуре —
сервер всегда отдаёт `index.html`, экран выбирает клиентский JS.

### `src/router.ts` (новый файл)

```ts
export type Route = { name: 'list' } | { name: 'task-detail'; id: number }
```

- `parseLocation(): Route` — разбирает `window.location.pathname` по
  `^/tasks/(\d+)$`; совпало → `{ name: 'task-detail', id }`; не совпало
  (`/`, `/tasks/abc`, любой другой путь) → `{ name: 'list' }`.
- `currentRoute` — `ref<Route>(parseLocation())`, реактивный источник
  текущего экрана для `App.vue`.
- `navigate(path: string): void` — `history.pushState(null, '', path)` +
  пересчитывает `currentRoute`.
- слушатель `popstate` на `window` — синхронизирует `currentRoute` при
  навигации назад/вперёд браузером.
- `onLinkClick(event: MouseEvent, path: string): void` — обработчик для
  внутренних ссылок: обычный клик (левая кнопка, без Ctrl/Cmd/Shift/Alt)
  → `preventDefault()` + `navigate(path)`; иначе событие не трогается —
  открытие в новой вкладке и переход правой кнопкой остаются штатным
  поведением ссылки.

### Слои и файлы

- **`src/App.vue`** — по `currentRoute.value.name` рендерит `TaskScreen`
  либо `TaskDetailScreen` (`v-if`/`v-else`), во втором случае прокидывает
  `id` пропом. Общий `<h1>Задачи</h1>` переезжает внутрь `TaskScreen.vue`
  — у экрана деталей будет собственный заголовок (название задачи).
- **`src/api/tasks.ts`** — новая функция `fetchTask(id: number): Promise<Task>`,
  вызывает `GET /tasks/{id}` через существующий `mapTask`. Отдельно
  проверяет `response.status === 404`, чтобы экран деталей мог показать
  «задача не найдена», а не общий текст ошибки.
- **`src/components/TaskListItem.vue`** — карточка оборачивается в
  `<a :href="`/tasks/${task.id}`" @click="onLinkClick($event, ...)">`
  (весь `<li>`, не только заголовок — крупная область клика, доступна с
  клавиатуры, работает как настоящая ссылка: видна в статус-баре браузера,
  копируется через «копировать адрес ссылки»). `StatusBadge` внутри
  остаётся некликабельным.
- **`src/components/TaskDetailScreen.vue`** (новый) — второй компонент,
  которому разрешено обращаться к `api/` (наравне с `TaskScreen.vue`; см.
  «Открытые вопросы» про формулировку правила в `AGENTS.md`). Получает
  `id: number` пропом, в `onMounted` параллельно вызывает `fetchTask(id)`
  и `fetchUsers()`. Отвечает за состояния загрузки/ошибки/404 и передаёт
  загруженные данные в презентационный `TaskDetailCard.vue`.
- **`src/components/TaskDetailCard.vue`** (новый) — чисто презентационный,
  без side-effects: `task: Task`, `assigneeName: string | null` пропами,
  рендерит название, `StatusBadge`, описание (или «Без описания»),
  исполнителя (или «Без исполнителя»), даты создания/обновления как есть
  (ISO-строка из ответа API — в проекте нет утилиты форматирования дат,
  добавлять её не входит в объём задачи), ссылку «Назад к списку»
  (`onLinkClick`). Вынесен в отдельный компонент сразу, а не оставлен
  частью `TaskDetailScreen.vue`, чтобы не упереться в лимит ~80 строк на
  файл (`apps/web/AGENTS.md`, раздел «Размер») — по образцу уже
  существующего разделения `TaskScreen.vue` (загрузка) /
  `TaskList.vue` + `TaskListItem.vue` (презентация).

Имя исполнителя резолвится так же, как сейчас в `TaskScreen.vue` — через
`Record<number, string>`, собранный из списка пользователей. Компонент
дублирует вызов `fetchUsers()` отдельно от `TaskScreen.vue`: в приложении
нет общего стора (запрещён `AGENTS.md`) и нет кеша, поэтому при переходе
на экран деталей список пользователей запрашивается заново — осознанное
упрощение для текущего размера приложения.

Поскольку переход список ↔ детали пересоздаёт дочерний компонент
(`v-if`/`v-else` в `App.vue`, а не один компонент с меняющимся пропом),
`TaskDetailScreen.vue` грузит данные один раз в `onMounted` — `watch` на
изменение `id` не нужен.

## Контракты

- HTTP: без изменений, см. «Бэкенд» выше.
- `router.ts`: `Route`, `currentRoute`, `parseLocation()`, `navigate(path)`,
  `onLinkClick(event, path)` — см. описание выше.
- `fetchTask(id: number): Promise<Task>` в `src/api/tasks.ts`, бросает
  `Error` с текстом, различимым по `response.status === 404` на стороне
  вызывающего кода.
- `TaskDetailScreen.vue` props: `{ id: number }`.
- `TaskDetailCard.vue` props: `{ task: Task; assigneeName: string | null }`.

## Открытые вопросы (нужно подтверждение перед реализацией)

Корневой `AGENTS.md` требует сверяться с `search_docs` по любому вопросу
о поведении продукта (что показывать/скрывать, как обрабатывать
состояния) — в этой сессии инструмент `search_docs` недоступен, поэтому
ниже — минимальные технические допущения по умолчанию, а не
подтверждённые продуктовые решения:

1. **Неизвестный путь** (`/tasks/abc`, случайный `/foo`) — по умолчанию
   тихо показывает список задач (`parseLocation` возвращает `{ name: 'list' }`),
   без отдельной страницы 404. Технически самый дешёвый вариант при двух
   экранах без роутера; продуктово не подтверждён.
2. **Кликабельная область карточки** — по умолчанию вся `<li>`, не
   только заголовок. Это более крупная и обычная цель клика, но не
   зафиксировано в issue явно.
3. **Правило в `apps/web/AGENTS.md`** («К `api/` обращается только
   `TaskScreen.vue`») называет один конкретный файл. Эта спека трактует
   правило по смыслу — «только экранные компоненты верхнего уровня
   обращаются к api, презентационные — нет» — и добавляет
   `TaskDetailScreen.vue` вторым таким компонентом. Формулировку файла
   не меняю в рамках этой задачи (правки `AGENTS.md` — отдельный вопрос,
   не входящий в её объём), но реализация полагается на эту трактовку.
4. В репозитории уже есть две другие ветки (`issue-19-no-agents-with-spec`,
   `issue-19-no-agents-no-spec`) с независимыми реализациями этого же
   issue — в одной без роутера (как в этой спеке), в другой с
   `vue-router`. Эта спека их не учитывает как источник ограничений
   (см. корневой `AGENTS.md`: спека опирается на код текущей ветки и
   явные указания в задаче), совпадение подхода с
   `issue-19-no-agents-with-spec` — следствие одинаковых ограничений
   `AGENTS.md`, а не заимствование.
